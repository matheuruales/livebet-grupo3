LiveBet: diseño, construcción y despliegue

Este informe explica el proyecto desde el código que se ejecuta, no desde una lista aislada de tecnologías. Cada decisión se relaciona con los contenidos estudiados en Programación Orientada a Objetos, Sistemas Distribuidos y Sistemas Operativos.

Resumen

LiveBet es una plataforma académica de apuestas deportivas en vivo que integra una aplicación web, seis servicios de negocio, dos intermediarios de mensajería y una base de datos relacional. El sistema crea partidos, permite apostar con un saldo simulado, programa el cierre de cada encuentro, genera un resultado, liquida las apuestas y comunica el desenlace por la interfaz y por correo. El propósito no fue imitar a escala comercial una casa de apuestas, sino resolver de forma coherente un problema donde varias acciones ocurren al mismo tiempo y no pueden depender de un único proceso.

La solución se desarrolló con Java 17 y Spring Boot 3.3.5. La lógica se organizó alrededor de un modelo de dominio rico: MatchAggregate contiene las reglas del partido; los estados controlan qué operaciones son válidas; y una estrategia independiente calcula los premios. Kafka conserva el historial ordenado de eventos. RabbitMQ programa trabajos diferidos y distribuye notificaciones. PostgreSQL mantiene saldo, apuestas y auditoría. Docker Compose reúne la infraestructura y los servicios, mientras una instancia EC2 con Ubuntu ejecuta el despliegue de entrega.

El resultado es un sistema funcional con registro, autenticación, roles, apuestas deportivas, ruleta compartida, recargas simuladas, historial personal y correos de resultado. La evaluación también identifica límites: el despliegue usa una sola máquina, el acceso público todavía es HTTP, los brokers no están replicados y las pruebas de integración pueden crecer. Reconocerlos permite valorar el proyecto con precisión, sin presentar como resuelto lo que corresponde a una evolución futura.

Palabras clave: arquitectura orientada a eventos, modelo de dominio rico, Kafka, RabbitMQ, PostgreSQL, Docker, Amazon EC2, idempotencia.

1. Introducción

Una apuesta parece sencilla desde la pantalla: el usuario elige un equipo, indica un monto y espera. Por debajo, el sistema debe coordinar tiempo, dinero, concurrencia y comunicación. Una apuesta enviada justo cuando termina el partido no puede aceptarse de forma arbitraria; un mensaje repetido no debe pagar dos veces; una caída temporal del correo no debe borrar la notificación; y un reinicio no puede dejar el saldo separado del registro de la apuesta.

LiveBet nació a partir de ese problema. La aplicación debía generar partidos aleatorios, registrar apuestas mientras estuvieran abiertos, cerrarlos automáticamente y mostrar el resultado en tiempo real. Durante el desarrollo se añadieron funciones de uso cotidiano —cuentas, roles, saldo, recargas, historial, ruleta y correos— sin abandonar las condiciones técnicas del ejercicio. Esto obligó a distinguir entre la experiencia visible y la infraestructura que sostiene el proceso.

El proyecto sirve como punto de encuentro para las tres asignaturas. Programación Orientada a Objetos aporta el diseño de las reglas y la separación de responsabilidades. Sistemas Distribuidos explica la comunicación por eventos, la consistencia, los reintentos y el comportamiento ante fallos. Sistemas Operativos permite comprender qué ocurre al ejecutar varios contenedores sobre Linux y cómo se administran procesos, memoria, archivos, redes y entrada/salida.

2. Problema, objetivos y alcance

La dificultad central consiste en mantener una historia coherente del partido cuando la información se produce en lugares distintos. El generador conoce el instante de apertura; la API conoce al usuario y su saldo; el simulador decide el marcador; el motor de resultados reúne los eventos; el dashboard muestra el cambio; y el trabajador de correo informa al apostador. Si todos dependieran de llamadas directas encadenadas, la caída de uno bloquearía a los demás y sería difícil repetir un paso sin repetir sus efectos.

2.1 Objetivo general

Diseñar, implementar y desplegar una plataforma distribuida que gestione usuarios, partidos, apuestas y resultados mediante un dominio orientado a objetos, comunicación asíncrona y contenedores ejecutados en una instancia de nube.

2.2 Objetivos específicos

  • Modelar las reglas del partido, el dinero y la liquidación sin depender de frameworks ni brokers.
  • Separar generación, recepción de apuestas, simulación, liquidación y presentación en componentes con responsabilidades identificables.
  • Conservar el orden de los eventos de un partido y evitar que un evento repetido produzca pagos duplicados.
  • Programar cierres y distribuir notificaciones con colas, reintentos y mensajes fallidos.
  • Empaquetar la solución con Docker Compose, verificarla y desplegarla en Amazon EC2.

2.3 Alcance

El alcance es un prototipo académico completo, no una plataforma de dinero real. Las recargas y los saldos son simulados. La aplicación acepta datos ficticios de tarjeta y conserva solamente una referencia y los últimos cuatro dígitos; no existe integración financiera ni cumplimiento PCI DSS. Esta decisión mantiene el trabajo dentro del objetivo pedagógico y evita tratar información bancaria real.

El desarrollo fue incremental. Primero se resolvió el flujo de partidos y apuestas; después se enriqueció el dominio, se incorporó persistencia, autenticación y roles, y finalmente se añadieron ruleta, recargas y correos. La entrega se valida mediante la suite Maven, la configuración Docker y pruebas funcionales sobre EC2.

3. Recorrido funcional y arquitectura

El recorrido comienza en match-generator. El servicio crea un identificador, selecciona dos equipos y publica MATCH_CREATED en el tópico match_events. Al mismo tiempo entrega a RabbitMQ un comando con retraso. El retraso representa la duración del encuentro y evita que el generador permanezca bloqueado esperando.

Cuando una persona apuesta, betting-api autentica el token, valida la solicitud y descuenta el monto. En la misma transacción guarda la petición y un evento pendiente en la tabla de outbox. Un proceso posterior publica BET_PLACED en Kafka. Cuando vence el retraso, match-simulator consume el comando, produce un marcador válido y publica MATCH_FINISHED. results-engine lee los tres tipos de evento, reconstruye el partido, determina ganadores y perdedores y persiste la auditoría. Finalmente envía notificaciones a RabbitMQ: dashboard-backend las transmite por WebSocket y email-worker prepara el correo.

match-generator → Kafka → results-engine → PostgreSQL
match-generator → RabbitMQ (delay) → match-simulator → Kafka
results-engine → RabbitMQ → dashboard-backend / email-worker

La ruleta mantiene una ronda compartida, restringe apuestas al periodo habilitado y liquida de acuerdo con el número final. La recarga actualiza el saldo mediante una transacción y emite un comprobante. “Mis apuestas” reúne eventos deportivos y jugadas de ruleta para que la actividad no quede fragmentada.

3.1 Responsabilidades desplegables

  • match-generator: crea partidos y programa su cierre.
  • betting-api: administra autenticación, usuarios, saldo, apuestas, recargas y ruleta.
  • match-simulator: recibe el temporizador y genera el marcador.
  • results-engine: reconstruye estado, aplica reglas, liquida y audita.
  • dashboard-backend: sirve la interfaz y transmite cambios por WebSocket.
  • email-worker: consume notificaciones y envía correos HTML; funciona con dos réplicas competitivas.

domain y shared-contracts son módulos compartidos de código, no contenedores independientes.

4. Programación Orientada a Objetos

4.1 Modelo de dominio rico

La clase más representativa es MatchAggregate. No es una bolsa de atributos con setters; representa un partido y decide qué puede ocurrir. Sus operaciones registran apuestas, cierran el encuentro y producen liquidaciones. El estado interno no puede modificarse desde un controlador para saltarse las reglas. Esa unión de datos y comportamiento constituye un modelo de dominio rico.

La diferencia se aprecia ante una apuesta tardía. BetService coordina la solicitud, pero no decide si el partido todavía acepta apuestas. Esa regla pertenece al agregado y a su estado. Por tanto, seguirá siendo válida si mañana la entrada proviene de otra API o de una aplicación móvil.

4.2 State, Strategy y objetos de valor

MatchState define operaciones según el momento del partido. OpenForBetsState permite apostar y cerrar. ClosedState impide nuevas apuestas y permite liquidar. SettledState es terminal. En vez de repetir condiciones en muchas clases, cada estado conoce sus transiciones. BettingClosedException e InvalidMatchTransitionException vuelven explícita una violación.

PayoutStrategy define el cálculo del premio y FixedOddsPayoutStrategy implementa la cuota fija. El agregado solicita el cálculo a una interfaz sin conocer la fórmula. Otra política puede incorporarse sin modificar las transiciones del partido, aplicación directa del principio abierto/cerrado.

Money, MatchId, BetId y UserId son records inmutables. Money rechaza cantidades negativas y usa BigDecimal para evitar los errores de double. Un dato inválido no viaja por varias capas: el objeto se niega a existir desde el inicio.

4.3 SOLID, puertos y adaptadores

La inversión de dependencias se observa en los puertos. BetEventOutboxPort separa el caso de uso de JPA; MatchEventPort y MatchTimerPort separan el generador de Kafka y RabbitMQ; FinishedEventPort separa el simulador de Kafka; y NotificationPort desacopla el motor de RabbitMQ. Las clases centrales dependen de contratos pequeños; los adaptadores conectan la tecnología concreta.

La responsabilidad única también aparece en el motor. EventProcessor clasifica contratos; MatchCreatedHandler, BetPlacedHandler y MatchFinishedHandler atienden casos diferentes; MatchRegistry conserva la réplica en memoria; y los repositorios persisten. El criterio no fue imponer un número de líneas, sino mantener un motivo principal de cambio por clase.

4.4 DTO, servicio y agregado

LoginRequest, RegisterRequest, RechargeRequest y RouletteBetRequest transportan y validan datos externos. BetService es un servicio de aplicación que coordina cuenta, repositorios y outbox dentro de una transacción. MatchAggregate pertenece al dominio y protege invariantes. Una solicitud pasa por BearerTokenFilter, un controlador con @Valid, el servicio y finalmente el dominio o repositorio. ApiExceptionHandler convierte errores conocidos en respuestas HTTP comprensibles.

5. Sistemas Distribuidos

5.1 Kafka: historia ordenada

Kafka conserva MATCH_CREATED, BET_PLACED y MATCH_FINISHED. Todos usan matchId como clave. Kafka calcula la partición a partir de esa clave, por lo que los eventos del mismo partido mantienen su orden aunque el tópico tenga tres particiones. La retención configurada es de siete días.

El consumidor no borra el evento al leerlo. Cada grupo mantiene su posición y el log permanece disponible durante la retención. results-engine puede leer desde earliest y reconstruir agregados después de un reinicio. Reproducir la historia debe reconstruir estado, no volver a pagar; de ahí la importancia de la idempotencia.

5.2 RabbitMQ: trabajo, retraso y enrutamiento

RabbitMQ resuelve tareas que no necesitan ser un historial largo. El exchange match.delayed recibe un comando con la routing key match.simulate y lo entrega a match_simulation_queue cuando vence el retraso. Si falla repetidamente, el mensaje pasa por un dead-letter exchange a match_simulation_dlq. Para notificaciones se usa un topic exchange que dirige mensajes al dashboard o al correo.

Un exchange no almacena mensajes como una carpeta. Recibe, examina routing key y bindings, y decide la cola. La cola retiene el trabajo hasta la confirmación. AMQP define publicar, enrutar y confirmar; TCP transporta los bytes de forma fiable y ordenada. Por eso AMQP normalmente funciona sobre TCP: el protocolo de mensajería necesita una conexión de transporte.

Kafka y RabbitMQ no son redundantes. Kafka responde “¿qué ocurrió y en qué orden?”. RabbitMQ responde “¿qué trabajo debe ejecutarse y qué consumidor puede tomarlo?”.

5.3 HTTP, HTTPS y WebSocket

HTTP se usa para registrar, iniciar sesión, consultar perfiles y ejecutar operaciones. En la entrega pública se utilizó HTTP sin cifrado; HTTPS añadiría TLS y es obligatorio antes de un entorno real. WebSocket mantiene un canal abierto entre dashboard-backend y navegador. Tras el saludo inicial, el servidor empuja el cambio sin consultas repetidas. Una lectura HTTP de estado permite recuperar la vista tras una recarga.

5.4 CAP, PACELC y consistencia

La aplicación no se resume honestamente con una sola etiqueta CAP. Dentro de betting-api, PostgreSQL prioriza consistencia: débito, apuesta y outbox se confirman o revierten juntos. Entre servicios hay consistencia eventual: el evento tarda un momento en aparecer en el motor y luego en el dashboard. Ante una partición, algunos componentes conservan trabajo para procesarlo al recuperar conexión.

PACELC añade la decisión en funcionamiento normal: aun sin partición, ¿menor latencia o mayor consistencia? LiveBet acepta una pequeña demora distribuida para no hacer depender la transacción del usuario de todos los consumidores. La confirmación local es consistente; la propagación es asíncrona. No se afirma alta disponibilidad global: Kafka, RabbitMQ y PostgreSQL son instancias únicas en una sola EC2.

6. Confiabilidad y tolerancia a fallos

6.1 Transactional Outbox

Si la API descontara saldo y fallara antes de publicar BET_PLACED, la base mostraría una apuesta desconocida por el motor. El patrón Transactional Outbox evita esa ventana: saldo, solicitud y evento pendiente se escriben en una transacción. BetOutboxDispatcher publica y marca el registro. Si Kafka no está disponible, el evento permanece en PostgreSQL.

6.2 Idempotencia y entrega

El sistema trabaja con entrega al menos una vez, no con una promesa global de exactly-once. Cada contrato incluye eventId y los consumidores registran cuáles procesaron. SettlementService protege estados terminales y la liquidación bloquea la apuesta antes de acreditar. La expresión correcta es “efecto único mediante idempotencia”.

6.3 Reintentos, DLQ y recuperación

RabbitMQ conserva trabajos no confirmados y usa colas de mensajes fallidos. Si el correo falla, el mensaje se reintenta y finalmente pasa a email_notifications_dlq. SettlementReconciler y OverdueMatchReconciler buscan estados que debieron avanzar. Al reiniciar, el motor reproduce Kafka y reconstruye MatchRegistry; los eventos auditados no repiten movimientos ni correos.

El material de clase estudia heartbeat, Bully y Raft para detectar fallos y acordar liderazgo. LiveBet no implementa consenso propio. Existe recuperación ante fallos temporales de procesos y comunicación, pero no tolerancia a la pérdida completa de EC2. Un sistema de producción necesitaría réplicas en varias zonas.

7. Sistemas Operativos y contenedores

7.1 Procesos aislados

Docker no crea una máquina virtual completa por servicio. Cada contenedor ejecuta procesos Linux aislados mediante namespaces y comparte el kernel de Ubuntu. Los cgroups limitan CPU y memoria; el sistema de archivos por capas aporta imágenes reproducibles; y la red virtual asigna nombres y direcciones internas. Por eso once contenedores consumen menos que once sistemas operativos invitados.

7.2 Procesos y memoria

Para Linux, las aplicaciones Java, PostgreSQL, Kafka y RabbitMQ son procesos e hilos planificados por el kernel. Compose declara health checks y reinicios. Si un email-worker termina, puede volver sin reiniciar el motor. Las dos réplicas compiten por la cola y RabbitMQ entrega cada mensaje a una de ellas.

Cada proceso usa direcciones virtuales que la MMU traduce a páginas físicas. La JVM administra su heap y Linux decide qué páginas permanecen en RAM. Si los contenedores superan la memoria disponible, el host puede usar swap o terminar procesos; por eso los límites y la observación de salud importan.

7.3 Archivos, volúmenes y entrada/salida

La capa escribible de un contenedor es desechable. PostgreSQL guarda su información en postgres_data, volumen que sobrevive a la recreación. docker compose down -v elimina ese historial. Los Dockerfile multietapa separan compilación y ejecución, reducen la imagen y ejecutan con un usuario no root.

HTTP, WebSocket, TCP de Kafka, AMQP, escrituras de PostgreSQL y SMTP son operaciones de entrada/salida. Mientras un hilo espera red o disco, el planificador puede ejecutar otro. El compose separa dos redes: messaging para Kafka/RabbitMQ y persistence para PostgreSQL. Solo dashboard y API publican puertos hacia el host.

8. Persistencia, seguridad y datos

PostgreSQL conserva usuarios, saldos, solicitudes, outbox, auditoría, rondas de ruleta y recargas. Kafka mantiene el orden temporal durante la retención; PostgreSQL conserva la vista consolidada y contable. Esta duplicación es intencional: el log permite reconstruir y la base relacional permite transacciones y consultas. Outbox e idempotencia enlazan ambos mundos.

Las contraseñas usan BCrypt con costo 12. Las sesiones se firman con HMAC-SHA256 por doce horas. Las rutas administrativas exigen ADMIN en el backend. Los DTO restringen formatos y valores; los errores no exponen trazas internas; los contenedores funcionan sin root; y las credenciales se inyectan por entorno. Gmail usa SMTP autenticado con STARTTLS.

No se almacena el número completo de tarjeta ni el código de seguridad. Aun así, la entrega no está endurecida por completo: falta HTTPS, rotación formal de secretos, CORS restringido, rate limiting, monitoreo centralizado, copias automáticas y alta disponibilidad. Las prácticas de hardening vistas en clase —reducir servicios, actualizar, proteger SSH, usar firewall, fail2ban, auditoría y respuesta a incidentes— son trabajo futuro.

9. Docker Compose y AWS

docker-compose.yml define PostgreSQL, ZooKeeper, Kafka, una tarea kafka-init, RabbitMQ y seis aplicaciones. kafka-init termina tras preparar el tópico; con dos réplicas de correo pueden crearse doce contenedores, pero once quedan ejecutándose de forma estable. ZooKeeper coordina la versión de Kafka utilizada; migrar a KRaft permitiría eliminar esa dependencia.

La composición declara messaging y persistence, además del volumen postgres_data. Los health checks controlan el orden real de disponibilidad. El despliegue se ejecutó en Amazon EC2 m7i-flex.large con Ubuntu 24.04, región us-east-2 y 40 GiB gp3. Dashboard usa el puerto 8080 y API el 8081. La IP no es elástica y puede cambiar al detener la instancia.

EC2 es infraestructura como servicio: el equipo administra Ubuntu, Docker y la aplicación. No se usó ECS ni Kubernetes. Todos los componentes viven en una máquina; Docker los aísla, pero una falla del host afecta al conjunto. Esta elección simplifica la demostración y al mismo tiempo define el principal punto único de fallo.

GitHub Actions ejecuta pruebas Maven, valida Compose, empaqueta y calcula checksum. Un runner autoalojado en EC2 despliega, espera health checks y verifica. Si falla, puede regresar al paquete anterior. Los valores sensibles se concentran en PRODUCTION_ENV y no deben imprimirse.

10. Pruebas y evidencia de calidad

La suite contiene 14 clases y 33 casos @Test. Se ejecuta sin iniciar Spring, Kafka, RabbitMQ o PostgreSQL, lo que mantiene las pruebas rápidas. Las pruebas de dominio cubren dinero, aceptación y rechazo, estados y premios. Las de servicios usan Mockito para verificar colaboraciones.

BetServiceTest comprueba que una apuesta válida debite, guarde la solicitud, cree el outbox y devuelva el saldo. BetOutboxDispatcherTest verifica publicación y marcado. SettlementServiceTest cubre ganancia, pérdida, reembolso y estados terminales. EventProcessorTest reconstruye secuencias, guarda auditoría, notifica y evita efectos repetidos.

También se prueban tokens, cuentas, recargas, ruleta, simulación, dashboard y correos. La ausencia de @SpringBootTest es consciente para la capa unitaria, pero no reemplaza integración. La mejora natural es Testcontainers con Kafka, RabbitMQ y PostgreSQL, más pruebas HTTP/WebSocket de extremo a extremo.

11. Resultados

Una cuenta puede registrarse, iniciar sesión, recibir saldo inicial, apostar, observar el cierre, consultar historial y recibir el resultado por correo. Si gana, el premio se acredita; si pierde, queda registrado; si la apuesta llegó tarde, se rechaza y reembolsa una vez. La recarga genera comprobante y la ruleta mantiene una ronda común para todos.

El logro principal no es solo la interfaz. MatchAggregate se prueba sin Spring; los puertos permiten cambiar adaptadores; el outbox cierra la brecha entre base y broker; y los identificadores permiten reprocesar. La ejecución en AWS demostró que el paquete sale del equipo local y opera sobre Linux con versiones, redes, volúmenes y arranque reproducibles.

12. Limitaciones y mejoras

  • Incorporar HTTPS con dominio, certificado y proxy inverso; restringir CORS.
  • Separar infraestructura en varios nodos o servicios administrados.
  • Migrar Kafka de ZooKeeper a KRaft tras validar compatibilidad.
  • Añadir rate limiting, rotación de secretos, backups, métricas, alertas y trazas.
  • Reemplazar ddl-auto update por migraciones Flyway o Liquibase.
  • Agregar Testcontainers y escenarios de caída de broker, red y base de datos.
  • Formalizar recuperación ante desastres y manejo operativo de DLQ.
  • Si dejara de ser académico, integrar pagos certificados y requisitos legales.

13. Conclusiones

LiveBet demuestra que una interfaz dinámica solo es confiable cuando las reglas y la infraestructura cuentan la misma historia. El dominio impide transiciones inválidas; PostgreSQL protege movimientos locales; Kafka conserva hechos; RabbitMQ distribuye trabajos; y Docker ofrece un ambiente reproducible sobre Linux.

La relación entre asignaturas no es decorativa. Los objetos definen una operación válida. El sistema distribuido decide cómo llega a otros procesos y cómo se repite sin duplicar efectos. El sistema operativo asigna CPU, memoria, archivos, red y aislamiento. Ignorar una capa vuelve frágil al conjunto.

El proyecto cumple el propósito académico y ofrece una base razonable, pero conserva límites claros. Existe recuperación e idempotencia, no exactly-once global; existe separación por contenedores, no alta disponibilidad; existe SMTP con TLS, pero no HTTPS público. Precisar esas diferencias permite defender el trabajo con argumentos y plantear mejoras realistas.

Anexo. Recorrido técnico de una apuesta

  1. El navegador envía POST /api/bets con token, partido, selección y monto.
  2. BearerTokenFilter valida la sesión y el controlador recibe un DTO validado.
  3. BetService localiza la cuenta, comprueba saldo y ejecuta el débito.
  4. La transacción guarda solicitud y evento pendiente en el outbox.
  5. BetOutboxDispatcher publica BET_PLACED con matchId como clave.
  6. results-engine pide a MatchAggregate registrar la apuesta.
  7. RabbitMQ entrega el comando diferido al terminar el tiempo.
  8. match-simulator publica MATCH_FINISHED.
  9. El motor liquida; SettlementService acredita o marca estado final.
  10. RabbitMQ distribuye al dashboard y al correo.
  11. El navegador recibe WebSocket y el usuario recibe la notificación.
